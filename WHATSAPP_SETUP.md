# WhatsApp AI triage

**Latest update:** see [WHATSAPP_ENGAGEMENT_SETUP.md](./WHATSAPP_ENGAGEMENT_SETUP.md) for the required additional migration, first-use consent, shorter website-oriented chats, admin usage reporting, and optional scheduled medication reminders. The original setup below describes the earlier triage foundation. Consent now gates symptom processing; it takes precedence over the earlier first-message bypass behavior.

The webhook remains `/api/whatsapp/webhook`. It shares the website triage instructions: focused questions, context-aware follow-up, urgency assessment, and suggested care categories. JSON assessments are validated and formatted as readable WhatsApp replies. It does not diagnose, prescribe, book care, take payment, link phone numbers to website accounts, or access patient records. The website's existing instruction text was extracted into a shared helper without changing it.

Greetings, `MENU`, `HELP`, and `HOW IT WORKS` show a branded welcome with an explanatory three-step image and three native WhatsApp reply buttons: Check symptoms, Ask health question, and Find a doctor. The image is exported from `public/whatsapp/getting-started.svg` to `public/whatsapp/getting-started.png`; deploy both with the code so Meta can fetch the PNG over HTTPS. RESET also returns this menu after clearing context. Menu content and routing are deterministic, so they do not use Gemini calls. Button/list IDs are validated against known choices; client-supplied labels are ignored. Typed button titles also work.

Check symptoms asks for the user's symptoms. Ask health question invites general health education, with triage when personal symptoms are described. Find a doctor gives the website sign-in and professional-selection steps, without claiming a booking or clinician connection. Genuine symptom messages bypass menus, even on a first message; greetings embedded in a symptom message are not treated as menu commands. MENU preserves context; RESET clears it. No additional SQL migration is required for the welcome/buttons beyond the triage-memory script below.

Required server environment variables: `GEMINI_API_KEY`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, and `NEXT_PUBLIC_SUPABASE_URL` (or `VITE_SUPABASE_URL`). Never prefix server secrets with NEXT_PUBLIC or commit their values. Optional: `WHATSAPP_GEMINI_MODEL` (default `gemini-2.5-flash`), `WHATSAPP_GRAPH_VERSION` (default `v24.0`).

1. Run `whatsapp_triage_memory.sql` once in the project's Supabase SQL Editor before deploying. It can be rerun safely. It adds two dedicated tables and a server-only RPC, without altering patient, payment, or appointment tables.
2. Ensure Netlify has the required environment variables and deploy the updated project. For local testing, `npm run dev` needs a public HTTPS tunnel before Meta can reach it.
3. No Meta changes are needed for an already working webhook. For new setups, verify `https://mobiledoc247.com/api/whatsapp/webhook` with your verify token, subscribe to `messages`, and ensure the app is subscribed to the intended WhatsApp Business Account.
4. Send `RESET` or `Hello` to see the welcome image and buttons. Tap each option and test follow-up with fictional symptoms. Test typed `MENU` and direct symptoms too. The bot accepts text and supported menu selections; incoming media and receipts are ignored. Use a system-user token for ongoing operation.

GET echoes Meta's challenge only with the correct token. POST verifies X-Hub-Signature-256 using the raw body and app secret, and filters to the configured phone-number ID. Failed generation/delivery returns 503 for retry. Logs contain error codes only, never tokens, message contents, or sender numbers.

Supabase retains up to 20 user/assistant messages per conversation. Context expires after 24 hours of inactivity and is ignored after expiry. Expired records are physically removed on the next webhook claim, not by a timed deletion job; schedule database cleanup if stricter deletion timing is required. A first-turn notice explains memory and RESET. `RESET`, `/reset`, `/start`, `NEW ASSESSMENT`, and `FORGET ME` clear context and previously sent response text; receipt IDs remain temporarily for deduplication. Phone numbers are HMAC-hashed with the app secret and sending-phone ID for session keys; raw sender numbers are not stored. Rotating the app secret starts separate sessions.

Tables have RLS enabled, no client policies, and explicit revocation from anon/authenticated roles. Only the server service role can access them or execute the turn function. Nothing is saved to clinical records or counted as a saved website triage report.

Database leases serialize turns per sender across Netlify instances. Completed duplicate deliveries do not regenerate or resend answers. Prepared answers survive failed sends, so retries do not repeat the history turn. Missing database setup fails explicitly with `WHATSAPP_MEMORY_SETUP_REQUIRED`, without a stateless medical fallback. No message content, sender numbers, or tokens are logged.

The webhook awaits API delivery and returns 503 on failure for Meta to retry. A connection lost after Meta accepts a send but before recording success can still cause a duplicate reply. For larger traffic volumes, move processing to a durable worker queue with fast acknowledgement, bounded retries, monitoring, and rate limits. AI triage is guidance, not clinical validation or emergency monitoring. No messages are sent merely by configuring the endpoint.

Checks: `node scripts/test-whatsapp.cjs`, `node scripts/test-whatsapp-triage.cjs`, and `node node_modules/typescript/bin/tsc --noEmit --incremental false`. Optional SQL integration test: install `@electric-sql/pglite` in a temporary test directory, then run `node scripts/test-whatsapp-memory-sql.cjs`. It defaults to `.codex/whatsapp-sql-check-local/node_modules/@electric-sql/pglite`; override `PGLITE_TEST_PATH` for another installation. It tests real Postgres locally without touching Supabase.
